Language

SyntaxCompiler Annotations

The goals of this language are as follows:

  • Create a low level programming language where the user has as much control over what happens as possible.
  • Seperate any compiler defined behavior from items created by the user with an annotation system.
    • @throwable annotation is required to work with the throw keyword, not implementing a Throwable class or interface, though extending a class or interface that implements the annotation would still allow for throwing.
    • @iterable for the use in for(Type val : iterable) loops.
    • Using annotations like @integer(8) on a type implies that the compiler can assign an integer literal to the type, and that the type is 8 bits wide.
    • Rule of thumb for keywords and annotations: use keywords for items that the compiler mostly needs to know on the frontend (such as access modifiers), things that affect syntax in some way (like instanceof operator), and annotations for things that need to be passed to the backend (backend needs to know how to iterate over a type), or things that can take on multiple values (assigning literals to a type).
  • Lock the user in to as little decisions (especially naming conventions) made by other people as possible. If they want to create a custom int class, let them, and give them ways to make it indistinguishable from the primitive. If they want to create a "method" on someone else's class (that works like a function created there and takes the this argument as the first (but hidden) parameter), let them. We've all had the moment of "this class needs a method for X", you implement the method as a static function, and get annoyed because everything else around it is object.method() while your one function is X(object) and you have OCD. No, just me? Sorry I didn't know.
  • Keep as much type information together as possible. No int *var[2] = {&3, &5}; where the base type, pointer information, and array information are in 3 different locations.
